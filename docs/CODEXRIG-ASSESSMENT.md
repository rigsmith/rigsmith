Codex equivalent of clauderig — assessment, September 5, 2026

A Codex equivalent is feasible. Build two thin command frontends over a shared state-management engine, with separate Claude and Codex adapters. Start with configuration portability, a durable sync queue, search, and carefully scoped session backup. Treat complete session recovery and Desktop account isolation as separate compatibility milestones.

This review covers repository commit `d9bb24b`, the installed `codex-cli 0.144.6`, schemas generated by that binary, current official documentation, and a read-only inspection of local Codex storage structure. No credentials or conversation contents were copied into this report. No account switching, remote writes, or live session migration was performed.

**What is actually reusable**

Clauderig has roughly 25,000 production Go lines under `internal/clauderig`, including around 9,850 in command handlers and over 5,200 in account/Desktop code. This is substantially more than a file copier, and changing the executable name and root directory would leave many hidden Claude assumptions.

| Allowlist walker, private-remote verification, backup mechanics, locking, retention, staging reconciliation | Extract shared mechanisms. Supply artifact classifications and remote/store identity as inputs. |

Codex configuration is layered, and untrusted project configuration does not load. Named configuration profiles are settings overlays, not independent account logins. In the installed release, `--profile NAME` uses `NAME.config.toml`; documentation dates the change away from nested profile tables to 0.134.0. See [config basics](https://learn.chatgpt.com/docs/config-file/config-basic) and [advanced configuration](https://learn.chatgpt.com/docs/config-file/config-advanced).

For shared customization, use a canonical skill/instruction source plus vendor-specific additions. Avoid installing the same skill through multiple roots or both a plugin and a standalone copy. MCP needs a common model with an escape hatch for vendor fields, not a lossy conversion into the smallest common schema. See [skills](https://learn.chatgpt.com/docs/build-skills), [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), and [MCP](https://learn.chatgpt.com/docs/extend/mcp).

**The durable queue should serve both vendors**

This incorporates John's preference from the review. The first useful shared feature is a local durable queue, initially adopted by Claude and then reused by Codex:

```text
Claude hook ── Claude event decoder ─┐
                                    ├─ durable local queue ─ worker ─ snapshot/scan/stage ─ Git
Codex hook ─── Codex event decoder ──┘                         │
                                                            └─ status/retry/error reporting
```

Use an atomic on-disk spool for the first implementation, unless the concurrency requirements justify an owned SQLite database. Either fits a single Go executable; a database should not be Codex's own application database. The worker can be another subcommand of the same executable. Automatic retry requires a managed worker/service or a defined restart trigger, not merely launching a disposable background child.

The queue contract should include:

- Durable acknowledgement only after the job is committed to local storage; restrictive permissions and no credentials in job payloads.
- Store-scoped serialization, including across both executables if they use the same staging repository.
- Debouncing ordinary turn events. Preserve the union of specifically requested session flushes; a normal sync must never downgrade a final flush.
- At-least-once processing with idempotent staging/pushing, retry backoff, restart recovery, and visible permanent failures.
- Explicit phases: queued, captured locally, committed locally, pushed remotely. A successful enqueue is not a successful backup.
- Preserve `pull` semantics, including configured fresh-machine auto-restore. Keep that startup path synchronous initially; a queued pull needs a readiness contract before it can provide the same bootstrap behavior. Do not introduce background restore over an established agent environment.
- Preserve foreground manual sync and a `--wait`/drain mechanism for scripts that require completion.
- A periodic reconciliation pass to discover missed hooks, interrupted agents, and unflushed tails.
- Retention and pruning must not delete data referenced by pending capture jobs.

There is an important race: queuing only a transcript pathname is insufficient if the vendor subsequently deletes that transcript. The capture design needs either an already-maintained local snapshot, a bounded final-tail capture, or explicit reporting that the final bytes could not be captured. A queue alone cannot guarantee that deleted source data remains recoverable. Subagent completion also needs adapter-specific handling.

Current Codex provides `SessionStart`, `Stop`, `SessionEnd`, and blocking `PreToolUse`. Hooks may be in `hooks.json` or TOML; non-managed definitions require local hash-based trust. `SessionEnd` is synchronous, defaults to one second, and permits at most three seconds. `Stop` requires valid JSON output on success, so ordinary CLI progress text cannot be its output. Shell calls normalize to `Bash`; patches report `apply_patch` with patch text in `tool_input.command`. Some tool paths bypass hooks. These contracts require dedicated hook-mode handlers. See [Codex hooks](https://learn.chatgpt.com/docs/hooks).

Claude's existing hooks directly invoke pull, sync, and final flush, making the queue valuable there too: reduced turn latency, fewer redundant commits, and durable offline retry. See [installed hook plans](/Users/john/Git/rigsmith/internal/clauderig/hooks/hooks.go:27).

**Where a direct port would fail**

1. **TOML and transcript secrets.** Adding `config.toml` to today's allowlist would take the raw-file path, bypassing field-level redaction and secret-preserving restore. Separately, non-JSON content scanning deliberately stops above 64 KiB, and smaller multiline transcripts do not receive general embedded-token scanning. The README's absolute secret claim is stronger than these protections. Before extraction, implement TOML-aware processing and an explicit transcript policy: scan incrementally, quarantine suspect captures, and distinguish sanitized searchable text from native recoverable artifacts. Do not silently corrupt replay data while redacting it. See [format dispatch](/Users/john/Git/rigsmith/internal/clauderig/engine/sync.go:244) and [scan limits](/Users/john/Git/rigsmith/internal/clauderig/redact/scanfile.go:32).

2. **Session formats and merge semantics.** The local Codex sample uses dated `sessions/YYYY/MM/DD/rollout-…jsonl` files with `session_meta`, `response_item`, `event_msg`, and `turn_context` records. Claude's `user`/`assistant` extraction and `uuid` deduplication do not apply. For the same Codex session edited on two machines, preserve divergent versions rather than line-unioning tool-call and compaction histories. An extension of `.jsonl` does not prove merge compatibility. See [current union policy](/Users/john/Git/rigsmith/internal/clauderig/mergepolicy/policy.go:112).

3. **SQLite is additional state, not a portable sync file.** This installation has `state_5.sqlite` with thread paths, titles, cwd, archive status, project associations, and other tables, plus separate history, memory, goal, and queue databases. These observations are version-specific. Do not Git-merge or overwrite live databases or their WAL files. Preserve approved logical metadata, use Codex-owned reconciliation where supported, and verify what survives reconstruction. Raw rollout backup is not evidence of complete Desktop recovery.

4. **Restore is not yet a proven public round-trip.** The installed schema exposes thread listing with optional rollout scan-and-repair and normal resume with a cwd override. But its experimental path-based resume is explicitly unstable, and history-based resume is marked for Codex Cloud and “DO NOT USE.” Neither should be the foundation of a supported importer. Prove a stopped-session restore into an isolated home, followed by discovery and ordinary resume, before advertising cross-machine continuation. Cross-OS validation must also cover tool paths, attachments, custom tools, and missing repositories.

5. **Guard action decoding.** The existing guard expects one `file_path` and a Claude tool-name registry. A Codex patch may add, delete, update, and move multiple files. Normalize all affected paths and inspect Git state in each actual target worktree. Keep the shared branch policy, but do not inherit Claude's categorical ban on session relocation. Guard hooks remain workflow assistance; repository protection and sandbox policy provide stronger enforcement.

6. **Credentials and Desktop isolation.** Codex can store credentials in `auth.json` or an OS credential store. Keep them machine-local and let Codex authenticate and refresh them. Isolated CLI homes need testing with both credential modes and shared customization roots. Do not assume Claude's Keychain service naming, UUID identity, Electron `--user-data-dir`, sidecars, or deep links work for Codex. See [authentication](https://learn.chatgpt.com/docs/auth) and [Claude account implementation](/Users/john/Git/rigsmith/internal/clauderig/account/account.go:1).

A Codex v1 allowlist should consider user config, named config profiles, instructions, rules, hook definitions, user-authored skills, and explicitly selected session artifacts. Exclude credentials, app databases, process locks, caches, shell snapshots, worktree checkouts, and downloaded plugin runtimes by default. Scheduling definitions need separate treatment to avoid restoring duplicate active jobs. Memories and attachments require explicit export policy rather than sweeping their storage directories.

**Codex opportunities, and where Claude remains ahead**

Codex supplies an open-source, language-neutral app-server protocol for authentication, thread history, approvals, and streaming. Its account-rate-limit and model-discovery methods could improve the account dashboard and diagnostics without parsing private files. Generate schemas from supported installed versions and gate optional capabilities. This is a useful Go integration surface, but it is not a universal state export API or a guaranteed connection to the running Desktop instance. See [app-server documentation](https://learn.chatgpt.com/docs/app-server).

Codex already supports importing another agent's setup and recent work. The documented CLI import includes Claude Code, with up to 50 chats from the preceding 30 days; the Desktop import supports additional sources and automatic updates. Evaluate that before building Claude-to-Codex conversion. Rigsmith's distinct value is user-owned backup, retention, cross-machine recovery, and unified management; native import does not establish those guarantees. See [agent import](https://learn.chatgpt.com/docs/import).

Codex's Desktop worktree handoff is designed to move a conversation between the local checkout and its worktree. Integrate with that workflow rather than applying Claude's path-slug workaround. This is a difference in workflow support, not a claim that Claude lacks worktrees. See [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

Claude also has an Agent SDK, streaming, resumable/forkable sessions, MCP, skills, and sandboxing. Those should not be presented as Codex exclusives. Claude's documented hook catalog is broader: for example, worktree creation/removal, configuration changes, tool failures, and teammate-idle events have no direct counterparts in the Codex hook catalog reviewed here. These are adapter capability differences; clauderig's current four-event design does not require most of them. See [Claude SDK](https://code.claude.com/docs/en/agent-sdk/overview), [sessions](https://code.claude.com/docs/en/agent-sdk/sessions), and [Claude hooks](https://code.claude.com/docs/en/hooks).

**Implementation shape and effort**

```text
cmd/clauderig/                existing compatibility frontend
cmd/codexrig/                 new frontend
internal/agentrig/           queue, sync orchestration, artifact plans, ledger, common policy
internal/clauderig/          Claude adapter and remaining Claude-specific integrations
internal/codexrig/           Codex codecs, sessions, hooks, account and app-server integration
core/                       existing Git, path and worktree infrastructure
```

Use small capability interfaces such as artifact discovery/restore, session catalog, config codec, hook codec, account access, and app launching. A normalized artifact should carry vendor, root/profile identity, kind, source version, retention class, content fingerprint, and restore requirements. Keep native payloads separate from the normalized search index. Vendor adapters select merge and path-rewrite policies. Unsupported features should be reported, not silently approximated.

Initially retain separate Claude and Codex staging repositories, with one shared engine implementation. A combined repository can be added with a versioned vendor namespace and migration plan. Do not require existing clauderig users to migrate their backup layout just to deliver the Codex binary.
