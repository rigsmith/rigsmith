rig resolves a project name the same way whether you type it or configure it. A bare `rig run` used to take the first project matching `defaultProject` while `rig run <that same name>` refused the same query as ambiguous — so a stale copy in a nested worktree could launch, look exactly like your app, and say nothing. Both paths now run one resolver: matching is tiered (exact > prefix > substring, and `rig cd` also subsequence) and stops at the best non-empty tier, so one exact hit is never ambiguous; remaining ties break by proximity to your working directory (the copy you're standing in, then the nearest common ancestor); and anything still tied is reported, never guessed — a picker on a terminal, and off one the candidate paths, what each copy is, and the exact `"exclude": [...]` line to paste into `.rig.json` (a path glob, since two copies share one name). When a default does resolve, rig echoes what it picked: `· defaultProject Tweed.App → ui/src/Tweed.App`. Nested git worktrees — a checkout inside the repo, holding a duplicate of every project — are now skipped during discovery altogether, which is where most of this ambiguity came from; `--include-worktrees` opts back in for a cross-worktree sweep. `rig info` leads its Projects section with a labelled summary of duplicate names (flagging the one that is your `defaultProject`) and names any nested worktree it is holding back, including whether its branch is already merged and `rig prune` would remove it.
